# 版本提醒与二开更新来源

## 版本命名规范

统一使用 `X.Y.Z-custom.N`，Git 标签为 `vX.Y.Z-custom.N`。前三段是已经完整同步并验收的官方版本，最后的数字是本项目在该基线上的定制发布序号。

| 发布内容 | 版本示例 |
| --- | --- |
| 已同步官方 0.2.21，首次按新规范发布 | `0.2.21-custom.0` |
| 增加自己的功能或修复，再次发布 | `0.2.21-custom.1` |
| 从其他二开接入代码并发布 | `0.2.21-custom.2` |
| 继续定制并发布 | `0.2.21-custom.3`，之后继续递增 |
| 已完整接入并验收官方 0.2.22 | `0.2.22-custom.0` |

官方新版本仅发布但尚未接入时，不修改前三段版本，也不归零定制序号。同步官方下一版时保留已经存在的定制；只有完成同步与验证后才开始新基线的 `custom.0`。序号按正式发布递增，不必按每个提交递增；不复用已发布标签或替换同版本安装包。

定制序号使用非负整数，不加多余前导零，例如 `.0`、`.1`、`.10`，不使用 `.01`。`backend/cmd/server/VERSION`、Git 标签、安装包及镜像均保留完整的 `custom.N`。完成官方 0.2.22 接入后，当前版本文件为 `0.2.22-custom.0`，不代表已经发布或部署。

## 后台行为

- 管理员进入站点时检查版本。页面保持可见时每 20 分钟重新检查；切回页面或窗口获得焦点时也检查缓存是否过期。下拉菜单的刷新按钮立即重新请求 GitHub。
- 官方正式 Release 来自 `Wei-Shaw/sub2api`。版本高于当前部署版本时，在版本号旁显示红点；展开后显示官方版本、发布说明链接和同步到二开仓库的提示。
- 实际可安装版本、安装包和在线回退列表只来自 `FrankJunhaoYe/franklybuilds-sub2api` 的正式 Release。官方提醒本身不会触发下载、合并或部署。
- 你的仓库尚未发布正式 Release 时，显示“我的仓库尚未发布正式版本”，仍然独立检测官方发布。不把主分支的新提交当成已发布、可安装的版本。
- 两个来源分别报告检查失败。前端在当前会话中保留已经检测到的更新提醒，同时显示检查未完成；首次检查失败时不显示绿色“最新版本”标记。
- 普通用户不请求管理员更新接口，也不显示红点或维护操作。

## 维护接入点

- 后端：`backend/internal/service/update_service.go` 分开处理官方通知与二开安装源。缓存携带仓库标识，升级前保存的官方安装包缓存不会被复用。
- 前端：`frontend/src/components/common/VersionBadge.vue` 显示红点和两个来源的状态，`frontend/src/stores/app.ts` 提供有有效期的缓存。
- 安装脚本：`deploy/install.sh` 的默认 Release 来源也是二开仓库。Docker 手动回退提示使用发布配置中的 `ghcr.io/frankjunhaoye/sub2api`。
- 更新和回退先比较官方基线，再按数字比较定制序号：`0.2.21 < 0.2.21-custom.0 < 0.2.21-custom.1 < 0.2.21-custom.10 < 0.2.22-custom.0`。官方提醒只比较前三段，因此 `0.2.21-custom.99` 仍属于官方 0.2.21。
- `custom.N` 是本项目的正式修订号。完整与 simple 发布配置均使用 `prerelease: false`、`make_latest: true`，避免带后缀的正式版被当作预发布而无法检测。发布工具拒绝不符合 `vX.Y.Z-custom.N` 的标签。
- 上游同步时保留上述来源区分、缓存到期刷新和定制回归，不将安装来源重新改回官方仓库。

源码部署继续从二开仓库拉取、重新构建并部署。二进制部署使用二开 Release；Docker 部署使用二开镜像并重新创建容器。只有二开仓库完成同步、发布且当前部署版本更新后，才会消除对应的版本差异提醒。

二进制部署发布新版本时，先按上述规则更新 VERSION，验证后为同一代码提交创建对应的 `vX.Y.Z-custom.N` 标签，再通过完整发布流程生成平台安装包和校验文件。发布成功后，已部署的旧 custom 版本可从版本菜单执行“立即更新”，下载自己的仓库的新版程序，完成后按提示重启。simple release 只发布镜像，不能替代二进制在线更新所需的安装包。

Docker 镜像中，网页更新需要应用进程能写入程序所在目录，因为下载与替换都发生在同一目录。新版主 Dockerfile 与发布镜像将程序放入可写的 `/app/bin`，入口脚本仍由 root 持有。已运行且程序目录不可写的旧容器需要先改用新版镜像并重建。通过网页更新的二进制保存在当前容器中，重建容器时使用所选镜像内的版本。

单纯修改 VERSION、推送提交或创建没有安装包的 Release，不等于已经提供可安装更新。本功能不会自动合并官方代码，也不会自动创建下一次发布。

## 验证

覆盖官方新版但二开未发布、两个来源单独失败、旧官方缓存失效、同版本检查、升级后提醒消失、二开回退来源、前端缓存到期、定时器清理和普通用户不检测。浏览器使用本地模拟发布数据检查红点出现、菜单链接及同步后红点消失；不代表已在生产环境下载或安装 Release。

自定义版本回归覆盖同基线的 `.0 → .1`、`.9 → .10`、官方基线切换后的序号归零、旧无后缀版本迁移、缓存重新比较、定制回退排序、非法命名拒绝、完整发布与 simple 发布的稳定版本配置、完整安装包命名和镜像标签保留后缀。
