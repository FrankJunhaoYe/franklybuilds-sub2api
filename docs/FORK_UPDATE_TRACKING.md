# 版本提醒与二开更新来源

## 后台行为

- 管理员进入站点时检查版本。页面保持可见时每 20 分钟重新检查；切回页面或窗口获得焦点时也检查缓存是否过期。下拉菜单的刷新按钮立即重新请求 GitHub。
- 官方正式 Release 来自 `Wei-Shaw/sub2api`。版本高于当前部署版本时，在版本号旁显示红点；展开后显示官方版本、发布说明链接和同步到二开仓库的提示。
- 实际可安装版本、安装包和在线回退列表只来自 `FrankJunhaoYe/franklybuilds-sub2api` 的正式 Release。官方提醒本身不会触发下载、合并或部署。
- 你的仓库尚未发布正式 Release 时，显示“我的仓库尚未发布正式版本”，仍然独立检测官方发布。不把主分支的新提交当成已发布、可安装的版本。
- 两个来源分别报告检查失败。前端在当前会话中保留已经检测到的更新提醒，同时显示检查未完成；首次检查失败时不显示绿色“最新版本”标记。
- 普通用户不请求管理员更新接口，也不显示红点或维护操作。

## 维护接入点

- 后端：`backend/internal/service/update_service.go` 分开处理官方通知与二开安装源。缓存携带仓库标识，升级前保存的官方安装包缓存不会被复用。
- 前端：`frontend/src/components/common/VersionBadge.vue` 显示红点和两个来源的状态，`frontend/src/stores/app.ts` 提供有有效期的缓存。
- 安装脚本：`deploy/install.sh` 的默认 Release 来源也是二开仓库。Docker 手动回退提示使用发布配置中的 `ghcr.io/frankjunhaoye/sub2api`。
- 当前沿用上游的三段数字版本比较。二开发布需保留所接入的上游版本号；同一个版本号重新上传安装包、仅修改后缀或只推送提交不会触发新的可安装版本提醒。预发布版本不会通过 GitHub 的 latest Release 接口提示。
- 上游同步时保留上述来源区分、缓存到期刷新和定制回归，不将安装来源重新改回官方仓库。

源码部署继续从二开仓库拉取、重新构建并部署。二进制部署使用二开 Release；Docker 部署使用二开镜像并重新创建容器。只有二开仓库完成同步、发布且当前部署版本更新后，才会消除对应的版本差异提醒。

## 验证

覆盖官方新版但二开未发布、两个来源单独失败、旧官方缓存失效、同版本检查、升级后提醒消失、二开回退来源、前端缓存到期、定时器清理和普通用户不检测。浏览器使用本地模拟发布数据检查红点出现、菜单链接及同步后红点消失；不代表已在生产环境下载或安装 Release。
